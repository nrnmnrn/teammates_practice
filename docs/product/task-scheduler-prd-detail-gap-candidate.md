# 修改版 PRD 的細節缺口候選

> 文件性質：**未核定候選**，只供團隊盤點 `hackathon-prd_modified.md` 的可執行性缺口；不是競賽規則、實作規格或 `build-handoff/` 文件。
>
> 產品決策仍暫停，直到主辦方回覆改題詢問。本文件的「建議答案」一律未批准，不能據此開發或宣稱比賽要求。

## 目的與讀法

這是完整性清單，不是擴張舊功能。目標是令團隊日後若核定候選，能知道每個比較如何得到同一答案。它不恢復 MiniGrid、任意程式碼、Planner／Reflection、自動重試、策略庫、強化學習、真實佇列或即時部署。

來源標籤：`原 PRD` 是 [hackathon-prd.md](../../hackathon-prd.md)；`修改 PRD` 是 [hackathon-prd_modified.md](../../hackathon-prd_modified.md)；`候選來源` 是 [task-scheduler-validation-candidate.md](task-scheduler-validation-candidate.md)。節名用於直接定位，不把任何來源說成主辦方事實。

`原 PRD` 本身也不是完全可直接實作：它列出多項策略與硬門檻，仍有公平性、同分與資料邊界等未定義處。因此以下不把「比原版更詳細」誤當作恢復原設計。

## 建議的決策順序

1. 先確認改題可否使用，再核定範圍與情境數。
2. 接著鎖定時間邊界、工作輸入、快照與策略規則。
3. 然後鎖定分數、搜尋目標、評測母體與接受門檻。
4. 最後才決定 AI 呼叫、紀錄與介面操作；不可看結果後回頭改前面三層。

## 手算驗證候選（只驗算規則）

此例不是競賽資料，也不證明產品效益。假設單節點在 t=30 空出，兩件都已到達：A 為 urgent、arrival=29；B 為 normal、arrival=27。權重採建議的 `(urgency=1, wait=2)`。

- A：`2 × 1 × 1 + 2 × (30−29) = 4`。
- B：`2 × 1 × 0 + 2 × (30−27) = 6`。
- 因 B 分數6高於 A 分數4，先派 B；這刻意展示等待補償可壓過 urgent，而不是隱藏該取捨。
- 若兩者分數同為4，先比 arrival，較早到者先；arrival 也相同才比 id。

驗收時應以這四項逐步算出相同結果，並另測兩權重皆0時退回 arrival／id。此例只驗證排序與算術；不涉及 deadline、完成、接受門檻或 AI。

## 非技術說明與下一步

這份清單像賽跑前先把量尺、起跑線和終點線畫清楚。若不先定義「最後一刻到的工作算不算」或「AI 在兩個測試中是不是同一個答案」，每個人都可能算出不同成績，卻以為是在公平比較。

它沒有讓作品變大，也沒有批准任何功能；它只列出日後可選的答案與檢查方式。仍未知的是主辦方是否允許改題，以及團隊是否採用這個候選產品。下一步需先由主辦方回覆改題詢問，再由團隊產品決策者依上述順序核定或拒絕各項候選。
