# 相較原 PRD 的修改摘要：為何移除 MiniGrid

> 文件性質：供團隊核定的比較說明；不取代 `hackathon-prd.md`，也不授權賽前建立競賽實作。

## 結論

新方案保留原 PRD 的核心價值：「工作負載突變時，AI 提出排程策略，系統用相同情境驗證，退步就拒絕」。主要改變是把 MiniGrid、任意程式碼執行及多層 Agent 流程移除，改成一個可重播的背景報表工作排程驗證工具。

此修改較適合七小時黑客松：可把時間用在公平比較、結果解釋與可靠展示，而不是維護與題目價值關聯較弱的環境框架。這仍是候選方向，須由團隊在正式開發前核定。

## 主要修改對照

| 原 `hackathon-prd.md` | 新候選方案 | 修改目的 |
| --- | --- | --- |
| Adaptive Scheduler Arena，以 MiniGrid 作為主要環境 | 排程策略檢驗台，使用固定背景報表工作與確定性模擬器 | 直接呈現排程問題，降低環境層負擔 |
| 隱含電商／Flash Sale 語境 | 報表工作突然湧入；不使用訂單、付款、庫存語義 | 避免產品範圍膨脹，也避免把示範誤說成真實交易系統 |
| 自訂 `MiniGridEnv`、`reset/step/render`、格子語義 | 工作表、兩個固定處理節點、事件表與快照 | 只保留排程驗證所需的狀態 |
| FIFO、SJF、Priority、Round Robin、EDF 等多種技能 | FIFO、Priority、九組有限權重搜尋，另加一次 AI 候選 | 降低策略語義、測試與展示複雜度，仍保留有意義基準 |
| AI 可產生 Code-as-Policy | AI 只能提出兩個 `0–2` 整數權重與理由 | 不執行任意生成程式；確定性程式掌握逐件派工 |
| Policy Sandbox、匯入／檔案／網路／資源隔離 | 移除任意程式執行與沙箱 | 七小時內不必同時解決安全隔離、資源限制與策略正確性 |
| Planner、Reflection、候選重試與 Deploy 動作 | 一次提案、一次評測；不自動反思重試、不即時部署 | 讓 AI 貢獻可追溯，避免抽到成功結果才停止 |
| Skill Library 與 JSON 策略長期保存 | 保存本次候選、輸入、結果與判定收據 | 先證明一次決策可驗證，再考慮長期記憶 |
| MiniGrid reward，供 RL 相容 | 逾期、未完成、等待等產品指標；固定評測門檻 | 不混淆訓練獎勵與產品接受標準 |
| 60 步環境回合、事件後評估 | 第 20 單位湧入、第 30 單位快照、第 30–90 單位分支重播 | 明確區分觀察資料、比較起點及比較期間 |
| 主要承諾偏向「模型適應產生政策適應」 | 承諾「讓人審查受限候選，通過固定門檻才接受」 | 不把 AI 一定改善或生產效益說成已證明事實 |
| 四區 Gradio 介面包含環境畫面 | 四區最小畫面：觀察摘要、AI 收據、全部結果、雙節點時間線 | 將可見重點放在因果與比較，不依賴格子動畫 |

## 移除 MiniGrid 的具體理由

### 1. 它不是本題要驗證的核心

MiniGrid 擅長以格子環境表達移動、位置、障礙與動作；本題真正要驗證的是「同一批工作在不同派工規則下，逾期與等待是否改變」。處理節點不需要移動或尋路，格子位置也不影響工作結果。保留 MiniGrid 會增加介面和環境工作，卻不增加排程證據。

### 2. 語義容易混用

原 PRD 同時使用訂單、Worker、Gymnasium action、RL reward、CPU 式策略等概念。這可能使評審誤以為作品在做作業系統排程或強化學習環境。新方案只定義背景報表工作：抵達時間、實際處理時間、優先級、絕對期限、固定節點、不可中途暫停，較容易說清楚資料何時可見。

### 3. 七小時的整合風險過高

自訂 MiniGrid 環境需同時處理 `reset`、`step`、觀察空間、動作空間、渲染、事件注入、隨機種子與狀態重播。再加上模型、沙箱、評測器與 UI，任何一層延遲都會壓縮公平驗證和彩排時間。移除後可直接測試同一快照、同一工作表和同一評測器。

### 4. 它會分散展示焦點

格子動畫容易成為視覺主角，觀眾卻未必看懂它如何造成逾期數或等待時間差異。新方案以雙節點時間線及策略收據連結「事件 → 提案 → 結果 → 接受／拒絕」，更直接支援評審判斷。

### 5. 公平性更容易被證明

新方案所有策略共用封存工作表、同一快照、同一比較期間與相同節點狀態；實際處理時間在派工時不可見。這比在環境中重跑多個 agent 動作更容易檢查，也避免不同策略消耗亂數次數造成隱性不公平。

### 6. 移除不等於降低技術含量

技術難點從「建一個環境」轉為「建立可重播且不偷看未來的評測流程」：固定輸入、限制 AI 權限、比較 FIFO／Priority／搜尋／AI、計入逾期與未完成，並正確拒絕退步候選。這些證據更貼近產品可行性，也更能支持 AI 是否真的有額外價值。

## 可能代價與誠實界線

- 不再展示 MiniGrid 或空間互動，因此不能宣稱解決導航、空間規劃或跨環境學習問題。
- 不再執行 AI 產生的策略程式，因此展示的是受限參數提案，不是 Code-as-Policy 研究。
- 固定合成工作表只能證明這些重播情境的結果，不能推論真實企業效益或泛化能力。
- 若 AI 沒有勝過 FIFO 或小型搜尋，仍可展示「安全拒絕」；產品承諾應收斂為可審查、可重跑的驗證流程。

## 建議核定順序

1. 團隊先確認是否接受「背景報表工作」作為唯一領域語義。
2. 凍結兩個驗證情境、工作表版本、快照時間與接受門檻。
3. 凍結 AI 權限：只提兩個 `0–2` 權重，一次呼叫，不得看未來或改門檻。
4. 只有上述內容核定後，才把最小介面交接給未來實作 Repo；原 PRD 保留作為歷史版本，不直接覆寫。

## 白話比喻

原方案像是先蓋一座有道路、格子和移動規則的遊樂場，再研究廚房如何排外送單；新方案直接做一個透明的廚房試菜台：同一批單、同一批廚師、同一時間，分別試幾種出餐順序。AI 只能建議「急單重視多少、久候單補償多少」，系統用固定規則檢查，變差就說不。這樣七小時內比較可能完成一場可信的實驗；但是否真的比簡單規則好，仍要靠現場重播結果決定。
