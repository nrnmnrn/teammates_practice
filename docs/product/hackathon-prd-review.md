# 給提案者：Adaptive Scheduler Arena 修改建議與七小時執行規劃

日期：2026-09-08  
審查對象：[hackathon-prd.md](../../hackathon-prd.md)  
文件性質：工程與參賽策略建議，供提案者及團隊討論；尚未核定為產品需求。

## 1. 我對這個構想的理解與判斷

你的構想是讓 AI 觀察突發訂單造成的壅塞，提出新的排程策略，再由程式用相同情境驗證，決定是否採用。它最值得保留的地方，是把「AI 的建議是否有效」變成可觀察、可比較的結果。這比只顯示 AI 的分析文字，更容易讓評審理解作品價值。

我的判斷是：**保留這個核心，但縮減目前 PRD，才適合七小時開發。** 原版同時要求自訂環境、產生程式碼、安全執行、策略記憶、反思、多指標驗證與完整介面。它們各自能做，組合起來卻有大量相依關係；最大風險是到最後才發現各模組接不起來。

成功條件應改成：在同一批模擬任務上，完整展示一次「事件發生 → AI 提案 → 新舊策略比較 → 採用或拒絕」，並能重跑、解釋結果。AI 沒有提出更好的策略時，正確拒絕也算系統成功；不能把每次都改善當成保證。

七小時可行性的估計，假設四人全程參與、個人工具與帳號已驗證、開賽後才建立實作、選定版本的 MiniGrid 能順利啟動。這是工程估計，尚未經實作驗證，不能視為工期承諾。

## 3. MiniGrid 要保留，但控制自訂範圍

建議保留一個自訂 MiniGrid 環境，讓它負責任務抵達、等待佇列、處理節點忙閒、時間推進與完成紀錄。排程策略只決定下一個任務；畫面從同一份環境狀態產生。內部可以有佇列模組，但不可再維護另一套獨立推進的模擬器。

七小時版本使用固定處理節點與有限的等待位置。Worker 是處理任務的節點，不是各自移動的機器人。先前討論中提到的移動、尋路與搬運，會增加碰撞、路徑和多角色控制問題，本版建議移除。

這個取捨仍有代價：訂單排程主要依靠自訂規則，MiniGrid 的空間任務特色利用有限。提案時應坦白說明它是可重播的受控模擬環境，不能宣稱「只有 MiniGrid 才能解決」。若原題要求導航或跨環境學習，應重新討論題目，不能靠名稱對齊。

PRD 第 5 節應先補齊以下契約，才能分工：

- 每一步固定依「任務抵達 → 分派 → 處理 → 更新紀錄」推進；同一步的截止期限判定方式要寫明。
- 明定 Worker 數量、等待容量、任務處理時間，以及滿載時是拒收、等待還是丟棄；拒收任務不能從成績消失。
- 區分 Planner 的輸入摘要與環境的 observation（觀察資料），不要把概念性的字串、清單直接當成可執行的空間定義。
- 將「請 AI 提案／比較候選／採用」留在外層控制流程，環境的 `step` 負責推進模擬，避免混用兩種動作層級。
- `reset` 必須清空本輪狀態；同一輸入及策略應產生相同結果；重新繪圖不得推進時間。

以上是待實作驗證的設計要求，本文未建立環境或競賽程式碼。

## 4. 建議修改的 PRD 範圍

| 原章節／內容 | 建議修改 | 原因 |
|---|---|---|
| 1–2：產品承諾 | 定位成「模擬環境中的排程策略驗證原型」 | 現階段沒有真實訂單、成本或生產環境證據。 |
| 3：五種初始策略 | 保留 FIFO（先到先處理）、Priority（優先級排序）及一種可調權重策略 | 減少不同演算法語義與測試負擔。 |
| 5：MiniGrid | 一個環境、一種突發事件、固定 Worker；移除移動與尋路 | 讓環境先形成可靠的完整流程。 |
| 6–7：Code-as-Policy、Sandbox | AI 只輸出允許的策略名稱、有限範圍權重與簡短理由 | 不執行任意生成的 Python，省下隔離執行與安全驗證工作。 |
| 6：Reflection（反思） | 顯示一次候選策略的理由與驗證結果；自動重試延後 | 每輪呼叫都增加等待與失敗分支。 |
| 8：Skill Library（策略庫） | 只保留本次執行紀錄；策略檢索及跨事件重用延後 | 優先證明一次決策有效，再談長期記憶。 |
| 8：固定改善 10% | 先定義主要指標與限制，再於開賽後用基準結果校準並凍結門檻 | 未量測前無法知道門檻是否合理；不能看了候選結果再調門檻。 |
| 9：四區介面 | 同頁顯示環境、新舊結果、AI 理由、採用狀態 | 減少即時串流和複雜互動。 |
| 10：90 秒劇本 | 作為隊內彩排版本；移除第二次事件與技能重用 | 正式簡報長度仍待確認。 |
| 11：單人承擔大量核心工作 | 拆開環境、評測、AI 整合、展示責任 | 避免所有工作等同一人完成。 |

「受限制的策略參數」也要驗證：未知策略、缺少欄位、非有限數值、超出範圍的權重都必須明確拒絕。AI 的預估成績只能算理由，實際成績由評測程式計算。評測門檻由系統持有，AI 不能修改。

## 5. 評測怎麼改，結果才可信

建議先用「逾期任務數」作為主要指標，同時列出完成數、未完成數、拒收數與延遲。p95（95% 已完成任務的延遲不超過此值）可以顯示，但不宜在樣本很少時作為唯一採用依據。

必須在 PRD 補上以下規則：

1. **先產生相同任務清單，再比較策略。** 固定 seed（隨機種子）只是手段；若兩種策略消耗亂數的次數不同，同 seed 仍可能得到不同任務。評測直接共用抵達時間、處理時間、優先級和期限。
2. **統一比較起點。** MVP 建議所有策略從相同初始狀態跑完整回合，AI 使用基準回合的事件後摘要提案。這是離線重播比較，不宣稱已完成真實系統的即時熱切換。
3. **統一比較區間。** 建議每回合為模擬時間 `[0, 60)`，第 20 步注入事件；事件後區間為 `[20, 60)`。這代表事件後 40 步，不是 60 步。主要結果先採完整回合，事件後統計另標示。
4. **未完成不能被忽略。** 回合結束時，已過期限而未完成的任務也計入逾期；尚未過期限者另外列出。拒收數獨立揭露，不能靠拒收困難任務製造改善。
5. **固定工作負載與容量。** 若所有策略都讓 Worker 持續忙碌，排序未必提高吞吐量。作品可以改善逾期或等待分布，不必承諾全部指標都提升。
6. **先凍結採用規則。** 候選須降低主要指標，且不能增加拒收、降低完成數，並滿足事先定義的各優先級服務限制；若不能全部滿足就保留基準。公平性限制的數值應在基準量測後、候選評估前固定。
7. **保留驗證情境。** 用一組情境給 AI 分析，另用兩組固定任務清單驗證，逐組揭露結果；不得把驗證結果再餵回去反覆調整後仍稱為獨立驗證。三組只能支持小型示範，不能證明泛化能力。

候選還應與固定 Priority 策略一起列出。只比 FIFO 好，不能證明 AI 比簡單規則更有價值。若 Priority 一樣好，就如實呈現；這時作品的價值是有紀錄、可拒絕的策略驗證流程。

「模擬 60 步」、「API 等待秒數」與「展示 90 秒」應分開設定。模擬可快速完成，播放可以慢速；不要讓畫面動畫阻塞評測。

## 6. 四人候選分工

依[團隊準備狀態](../operations/team-readiness.md)提出以下建議，仍需團隊確認。原 PRD 的 Neo 未與此名單明確對應，不應自行認定身份。

| 成員 | 主要責任 | 最早交付與界線 |
|---|---|---|
| 于喬 | 技術整合負責人、共用資料契約、Planner 串接、合併與故障裁切 | 第 30 分鐘定契約；第 3 小時完成一次合法 AI 輸出。避免同時主寫環境與簡報。 |
| 咏宸 | MiniGrid 環境、任務生成、原題對齊與展示敘事 | 第 1.5 小時交付可重跑環境；第 4 小時前完成環境必要工作，再轉簡報。此分配不假設已熟悉 MiniGrid，前 30 分鐘需驗證接手能力。 |
| 家紳 | FIFO、Priority、參數策略、評測與採用判定 | 第 2 小時交付固定任務比較；不承擔策略庫或自動反思。由于喬優先審查指標計算。 |
| 昊祁 | 最小介面、結果呈現、展示操作與重播 | 第 1.5 小時用靜態範例接好畫面；第 3 小時接真實結果。不重算 KPI、不另建模擬狀態。 |

團隊資料顯示部分成員的 AI 輔助開發經驗較少，因此不把四人當成四條完全獨立的產線。于喬須保留協助與審查時間。若咏宸無法接手環境，由于喬接環境、咏宸接簡報與 Planner 輸入敘事，同時將 AI 功能縮成單次提案，避免總工作量不變卻增加主程式負擔。

每個檔案組只指定一個主要修改者；評測共用環境，不複製規則。前 30 分鐘只約定必要欄位：任務、策略設定、回合結果、比較判定。用文字與範例資料確認介面，不設計龐大通用框架。整合負責人可依預先約定的停損表停加功能；題目方向及提交範圍仍由團隊決定。

## 7. 七小時時間表：第五小時後停止加功能

以下相對開賽時間共 420 分鐘；實際起訖以主辦方通知為準。各欄並行執行，但每個檢查點都要驗證同一份整合版本。

| 時間 | 核心與整合 | 評測與展示 | 檢查點／落後時處置 |
|---|---|---|---|
| 0:00–0:30（30 分） | 確認最小範圍、環境啟動、資料契約及負責人 | 定義指標；列出三張簡報的問題、方法、證據 | 環境無法啟動就由整合負責人協助，立即取消裝飾性畫面工作。 |
| 0:30–1:30（60 分） | MiniGrid 可 reset/step；一批固定任務與 FIFO 跑完 | 介面用靜態範例呈現；手算一小批任務的預期結果 | 必須有可重跑回合；未完成則全力支援環境，暫停 AI 串接。 |
| 1:30–2:30（60 分） | 加突發事件、Priority、參數策略；接通環境與結果 | 評測與手算案例一致；UI 顯示真實結果；凍結判定規則 | 必須完成不依賴 AI 的比較流程；否則刪除非必要圖表，集中修正。 |
| 2:30–3:30（60 分） | 串接單次 AI 提案、輸出驗證、失敗狀態 | 同一批任務比較候選，顯示採用或拒絕 | AI 未接通時以明確標示的測試候選驗證整合；不宣稱 AI 已完成。 |
| 3:30–4:30（60 分） | 完成一鍵執行與結果保存；處理 API 失敗 | 跑兩組額外驗證；展示拒絕退步策略；完成簡報初稿 | 完整流程仍不穩，就停止所有延伸功能，必要時使用靜態結果圖。 |
| 4:30–5:00（30 分） | 修核心缺陷，凍結功能 | 核對敘事與真實結果；保存成功執行的重播資料 | 第五小時起只修阻止執行、結果錯誤與展示故障。 |
| 5:00–6:00（60 分） | 跑相關測試、lint；有配置才跑型別檢查；依 README 從乾淨環境啟動 | 驗證 API 超時、非法候選、重設與重跑；取得展示錄影 | 啟動或成績不可信時優先修正；不能以挑選結果掩蓋失敗。 |
| 6:00–7:00（60 分） | 檢查提交內容與啟動指令；保留最後修復空間 | 彩排兩次、核對投影可讀性、切換重播演練、完成提交 | 不再加新功能；依正式截止時間提前提交。 |

關鍵路徑是「環境 → 基準策略 → 評測 → AI 候選 → 展示」。介面與簡報可以提早用範例並行，但不能到最後才接真實資料。七小時不應全部拿來寫功能；最後兩小時是交付工作的一部分。

## 8. 失敗時怎麼收斂，仍保有可信展示

- **API 超時或輸出不合法：** 明確顯示原因並保留基準策略。可以播放先前真實成功執行的資料，但須標示「重播」；人工設定候選標示「測試策略」。
- **AI 候選沒有改善：** 展示拒絕與指標。可以解釋這保護了系統，不能宣稱性能提升，也不要無限重試直到抽到好結果。
- **即時動畫不穩：** 保留由環境產生的前後畫面及結果表，取消動畫；這比重新建立一套視覺化邏輯更省時。
- **MiniGrid 在第 1.5 小時仍無法完成回合：** 核心可行性已亮紅燈。縮到最小環境與一種策略繼續修；若仍無法完成，只能如實展示已完成部分，不以假畫面聲稱整合完成。
- **第五小時仍有錯誤成績：** 優先修成績計算，捨棄額外驗證圖表與介面美化。不能把尚未驗證的改善數字放進簡報。

## 9. 展示內容與完成標準

90 秒僅是建議彩排版本：前 15 秒說明突發任務與服務期限；15–30 秒展示基準壅塞；30–45 秒顯示 AI 建議及限制；45–70 秒展示相同任務下的比較；70–90 秒交代採用／拒絕、失敗處理與已知限制。正式時間確認後再調整。

另準備一頁 Codex 使用證據：例如它協助建立環境、產生指標測試或定位一次整合錯誤，以及團隊如何驗證。產品執行時呼叫 OpenAI 模型，與開發時使用 Codex 是兩件事；展示應說清楚各自貢獻。台灣站評審關注項目的隊內來源見[比賽資訊](../competition/README.md)，不要自行加上未確認比重。

最小完成標準：

- MiniGrid 參與真實狀態推進，固定任務與策略可重跑得到相同結果。
- FIFO、Priority、AI 候選使用相同任務清單及評測區間。
- 至少取得一次真實 AI 策略輸出；無法取得時，清楚列為未完成項目。
- 手算小案例能驗證逾期、完成、未完成與拒收計數。
- 非法候選與退步候選會被拒絕，基準保留；不需真的執行錯誤策略。
- 結果同時揭露主要情境與額外驗證的表現，標清缺少的驗證。
- 依啟動文件可以開啟展示；有已標示來源的重播備案。
- 完成相關測試與 lint；存在型別配置及 pre-commit 設定時，執行對應檢查並處理失敗。

賽前依[準備時程](../operations/schedule.md)驗證工具與合作流程，使用與參賽題目無關的練習。這份文件不授權賽前建立競賽環境、策略實作或 Agent 流程。

## 10. 給提案者的修改優先順序

先改第 3、6、7、8 節，把範圍縮到一次受限制的策略提案與可信比較；再改第 5 節，明確寫出 MiniGrid 的狀態與時間責任；最後依第 11、12 節重排人力、檢查點與完成標準。題目變更得到答覆後，再由團隊決定是否採用。

**給非技術成員的說明（ELI5）：** 我們要做的是一個小型訂單實驗場。訂單突然變多時，AI 建議改變處理順序；系統拿同一批訂單試跑，確認有幫助才接受。七小時先把這一次實驗做準、做完整，讓觀眾看得懂結果。
