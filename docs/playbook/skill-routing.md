# Skills 情境對照表

本頁是「先選對流程」的快速入口，不是每個 skill 的完整教學。實際可用的 skill 名稱與版本尚待核對；不可假定已有凍結 manifest。

## 使用原則

- 一次處理一個清楚、可驗收的目標；不要因為 skills 很多就全部使用。
- 先做短檢查：確認目標、證據、影響範圍與可驗收結果，再選流程。
- 人決定需求、範圍、優先順序與發布；skill 不代替此判斷。
- skill 的建議不會取代人對 diff、來源與結果的檢查。
- 下表為已核可操作指引；跨組員流程尚未演練。它不保證省 token 或提高正確率。
- 執行任何 skill 前，先核對該成員環境確有此 skill，並讀完其 `SKILL.md`。找不到歷史名稱時，不假裝已執行、不自行安裝，也不另定等價替代；回報缺少的步驟或請人釐清。

| 適用情境 | 不適用 | 做法 | 可觀察產出 |
|---|---|---|---|
| 想法、需求或名詞仍模糊，需要共同決定 | 已有清楚且小的實作任務 | `grill-with-docs`，由人確認決定後才進下一步 | 共同理解、必要名詞、決策紀錄 |
| 缺資訊、文件矛盾或卡住，尚不能說明原因 | 原因與最小修正已明確 | 先用 `investigate-first` 分開觀察與推論，列證據與可否證假設；證據足夠才改動 | 原因或精確 blocker、支撐證據 |
| 要做一個明確行為，且可先寫測試 | 需求或成功條件尚未確定 | `tdd`，先令測試失敗，再作最小實作與重構 | 失敗測試、最小實作、通過證據 |
| 難重現、原因不明的程式錯誤、偶發錯誤或回歸 | 已能直接指出小範圍修正 | `diagnosing-bugs`，先建立可重現的紅色檢查，再找原因與回歸測試 | 可重現證據、原因、回歸測試 |
| 已核可 Ticket 的實作 | 需求仍由人決定、或無明確驗收 | `implement`：依 Ticket 實作、測試、review；以 repo 工作流程為先。未獲 commit 核可不 commit；已明確授權則不重問 | diff、測試結果、review 結果、待核可 commit |
| 需要定位、最多兩檔的有界修改，或精簡 diff review | 新功能、跨切面重構、三檔以上修改 | `cavecrew`：位置未知先用 investigator；builder 只在位置已知時改最多兩檔；reviewer 只回精簡 findings。多檔改動交一般實作者或主線，不強用 builder | `path:line` 定位、最多兩檔 diff，或 findings |
| 要檢查變更是否符合要求與既有標準 | 尚無可檢查的 diff | `code-review` | review 結果、需修正事項 |
| 已完成實作與必要驗證，要整理狀態並準備交由人提交 | 尚有 blocker、未驗證或未完成工作 | `task-closeout`：核對 tracker／spec 與 Git；只請求 commit 批准，不自行提交 | 狀態、下一步、精確 commit 核可請求 |
| 換 session 或工作 blocked，需讓下一位安全續作 | 以為可代替完成驗證或 closeout | `handoff`：寫入 OS 暫存區；摘要既有文件未記錄的進度、假設與 blocker，既有規格、issue、測試、review 與 diff 只引用 | 暫存交接文件、既有 artifact 連結、未完成／blocker |
| 需要查證外部事實或案例 | 問題可由 repo 內既有文件回答 | `research`，保留直接來源並分開事實與推論 | 附直接來源的研究筆記 |

`/compact` 只在對話長度或可讀性需要時自行判斷；不是 `task-closeout` 前置，也不代表工作完成。

## 新增或修改對照項目的核可條件

每一項都要能說明：何時使用、何時不要使用、使用後應得到什麼結果。若內容來自 owner 的實務經驗，應依 [Codex 實務經驗](codex-practices.md)的核可流程檢查後再加入。
