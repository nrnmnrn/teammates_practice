## Behavior Principles

> 本檔是通用範本，不適用於本 planning repo。競賽實作須使用完整 `build-handoff/`，不可只複製本檔；交接包已提供自足的精簡 `AGENTS.md`。

## 承接與工作流程

- 承接時讀 `CONTEXT.md`（純術語）、`ARCHITECTURE.md`（現有與預定狀態須明標）、`PRD.md` 與目前 Ticket。子 PRD 文件與父子 issues 僅在拆分計畫獲核可後依實作 repo 的實際路徑加入。
- 開始、卡住、完成或換 session 時讀 `WORKFLOW.md`。交接包已提供上述檔與短版 `WORKFLOW.md`；複製本範本後依實作 repo 實際路徑調整。
- 動態認領工作；每份子 PRD 通常 2 張、最多 3 張 Ticket；一次 session 只做一張可執行 Ticket。已有處理者或同檔修改時先協調。
- 依 `WORKFLOW.md` 的流程入口選 skill；未獲明確核可不得 commit。已獲明確核可時可直接執行，不必重問。

- Think before coding. State assumptions explicitly. If uncertain, ask.
- Simplicity first. Minimum code that solves the problem. Nothing speculative.
- Surgical changes. Touch only what you must. Clean up only your own mess.
- Goal-driven execution. Define success criteria before coding. Loop until verified.
- Prefer existing patterns. Reuse current conventions. Do not introduce new abstractions unless necessary.

## Commands

- 依實作 repo 的 `pyproject.toml`、lockfile 與文件執行實際可用的 `uv` 命令。
- 非程式文件變更只跑 `git diff --check`；不要跑測試、lint 或型別檢查。

## Boundaries

### ✅ Always
- For code changes: run relevant tests and lint checks. Run type checking when the project has type-checking configuration.
- Write or update tests for changed public behavior.
- Handle errors explicitly (no silent catches).
- Use the project's logger instead of `print()` for diagnostic output.
- Ensure git commits list only human authors.

### ⚠️ Ask First
- Adding new dependencies (especially large ones).
- Database schema changes or migrations.
- Changes to authentication or authorization logic.
- Modifying CI/CD configuration.
- Removing or skipping tests.

### 🚫 Never
- Commit, view, or access secrets, API keys, or `.env` files.
- For spec-only or non-code documentation changes: run `git diff --check`; do not run tests, lint, or type checks.
- Force push to main/master.
- Edit an already-applied migration.
- Skip pre-commit hooks (`--no-verify`).
- Delete or modify production data directly.
- List AI agents as commit authors or co-authors.
- Weaken validation or authorization to make a test pass.


## Generated Files

- Do not manually edit any file with a `Generated by ... DO NOT EDIT` header.
- Do not manually edit lockfiles (`poetry.lock`, `Pipfile.lock`, `uv.lock`).
- Do not manually edit migration files after they have been created or applied.
- If a file appears to be auto-generated but lacks a header, ask before editing.
- To update generated code, modify the source of truth and use the project's documented generation command.
- If no generation command is documented, ask the user how to regenerate.

## Git Workflow

- Do not push, merge, or deploy without approval.
- Keep commits focused; do not mix unrelated formatting changes.
- Keep migrations and generated files in the same change as the code that requires them.
- If the project uses pre-commit hooks, run them before finishing: `pre-commit run --all-files`

## Sub-agent Routing

- Sol stays in primary task for planning, architecture, judgment, and final synthesis only.
- Terra handles bounded implementation requiring context and judgment.
- Luna handles clear, repeatable, verifiable tasks: tests, searches, mechanical edits.
- Give every worker: explicit scope, constraints, expected output, and done evidence.
- Isolate subagent context (fork_turns: "none" / fork_context: false).
- One writer per file set. Fresh read-only agents for independent review.
- Stop if required model is unavailable — do not substitute.
- Product, permission, and release approvals stay with the user.

## Completion Report

After completing a task, report:
- Summary of behavior changed
- Modified files
- Commands executed and their results
- Assumptions made
- Known limitations or remaining risks
- **ELI5 (Plain-language explanation):** Explain the outcome fully for a stakeholder with no technical background:
1. What this work changed or established;
2. Why it was necessary, and what misunderstanding or risk it prevents;
3. One familiar analogy or small everyday example that illustrates the most important
judgment;
4. What is still unknown, and therefore what cannot safely happen yet;
5. What information or action is needed next, and from whom.

Avoid acronyms, code, field names, and implementation details. If one is. unavoidable, explain it in plain language first. Do not reduce this to a one-sentence summary; a reader should understand the current state, reason, and impact without reading the technical sections.
