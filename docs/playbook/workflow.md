# 一個任務的標準流程

## 1. 讀懂任務

Issue 至少要有：問題、預期行為、驗收條件、不做的範圍。缺少任何一項時先詢問，不要自行補出大型需求。

每輪 session 開始前，先讀所屬子 PRD、總 PRD 的共同規則、目前 Issue、其 blocking edges（必須先完成的依賴關係）是否完成，以及最新整合狀態與前輪未解事項。依 blocking edges 排工作，不依純票號。若依賴未完成，改選可執行 Issue 或回報 owner，不自行繞過。

可對 agent 說：

```text
請先重述這個 issue 的目標、驗收條件與不做的範圍。
先不要修改檔案；列出你需要查看的最少檔案與理由。
```

## 2. 建立短分支

從團隊指定的基準 branch 建立一條只處理此 issue 的短分支。分支名稱包含類型與目的，例如 `feat/failure-trace-view`。不要在共用主分支直接開發。

## 3. 先建立失敗的驗證

使用 `tdd` 流程：先新增能代表需求的測試，執行它並確認失敗原因是功能尚未存在，而不是環境損壞或測試寫錯。

## 4. 實作最小修改

要求 agent 只做到當前測試通過。不要順便大改架構、換套件、整理所有檔案或新增未要求功能。

## 5. 執行回饋迴圈

依 repo 實際指令執行：

- 目標測試。
- 全部測試。
- formatter／linter。
- type checker。
- 與使用者操作相關的實際流程。

若 repo 尚未定義指令，停止並請 owner 確認；不要發明多套互相衝突的工具。

## 6. 閱讀 diff

逐項回答：

- [ ] 每個修改檔案都與 issue 有關。
- [ ] 沒有 secrets、個資或大型產物。
- [ ] 沒有刪除或放寬原有測試來換取通過。
- [ ] 錯誤處理與失敗模式可理解。
- [ ] 新測試在修正前確實會失敗。
- [ ] 驗收指令及結果已記錄。

看不懂的修改，不提交。請 agent 用簡單語言逐段解釋，或找于喬 review。

## 7. Commit 與 Pull Request

Commit 只包含一個目的。Pull Request 說明：做了什麼、為什麼、如何驗證、已知限制及 demo 影響。每張 Issue 完成後，跑既有測試、AI review 與人類核對；可安全整合的成果及早合併，不等待整個子 PRD。子 PRD 的全部 Issue 完成後，另做完整驗收。由于喬負責 `main` 最終合併，高風險 Agent loop 採獨立人類審查。

## 8. 發現範圍或規格問題

原承諾做錯或漏拆時，在原子 PRD 補 Issue。規格歧義或矛盾時，停止受影響工作，由于喬澄清，Neo 做領域核對。新增獨立成果時，由于喬建立新子 PRD 與 Issue。成員不得自行擴增需求。
