# 下一個 session：AI／Agent 類黑客松經驗研究提示詞

> 用途：將下列提示詞完整貼到新的 session 執行。研究對象不限於 Sea × OpenAI；產出是參考先例與參賽經驗，不是本隊的流程規定、產品需求或台灣站規則。

```text
請在此 planning repo 進行「AI／Agent 類黑客松的參賽經驗研究」。請使用繁體中文、對初學者友善地撰寫；必要的英文術語第一次出現時請簡短解釋。

目標
1. 研究至少兩場彼此不同、與 AI、AI-native 或 Agent（可依資料做判斷或執行任務的 AI 系統）相關的黑客松。
2. 每場至少找出一個具備下列兩種證據的案例：
   - 官方主辦方的得獎／成果公告；以及
   - 可檢視的作品證據，例如公開 repository、demo、簡報、影片或團隊技術文章。
3. 另蒐集參賽者的公開經驗：復盤文章、訪談、技術文章或公開貼文。重點是他們如何做取捨，而非只描述最後作品。

研究問題
- 他們如何從寬廣題目縮小到可展示的問題？
- 哪些功能、資料來源或技術選項被放棄？公開理由是什麼？
- 他們如何選擇 demo 的主線，讓評審或使用者能理解價值？
- 遇到資料、時間、可靠性、部署或團隊協作限制時，採取了什麼取捨？
- 回顧中有哪些失敗、後悔、意外或「若重來會改變」的內容？

來源與判定規則
- 對主辦方、賽事、得獎資格、規則或評分的事實，必須引用官方直接來源。
- 對作品功能，優先引用作品 repository、demo、簡報或團隊自己的技術文章。
- 對參賽感受與決策，只能寫成該參賽者的經驗分享，並清楚標示來源；不要當成普遍事實。
- 若只能找到新聞、社群轉貼或單一貼文，標為「補充來源／待補原始來源」；不得用來確認賽制事實或跨案例模式。
- 不可把任何其他黑客松的規則、時程、評分方式或資源，寫成 Sea × OpenAI 台灣站的已確認規則。
- 不要捏造細節；查不到時明確寫「尚未找到直接來源」。

建議產出與檔案邊界
- 在 docs/research/ 新建「一場賽事一份」研究筆記；檔名使用 YYYY-主辦方或賽事-地點或名稱.md，年份不確定時明確標註待核對。
- 每份筆記至少包含：研究範圍、直接來源、補充來源、來源事實、作品案例、參賽經驗、研究推論、限制與本隊差異、未決問題。
- 每項「參賽經驗」使用固定欄位：來源證據、公開經驗、可供未來討論的問題、限制／風險、待核實項目。
- 更新 docs/research/sea-openai-winning-patterns.md，僅作為研究導覽；除非至少兩個不同賽事有可比較且直接來源支持，否則不要新增跨賽事共通模式。
- 不建立 team-playbook、角色分工、時程、工作流程或產品規格；不要修改 build-handoff/。
- 不讀取、不修改、不暫存 hackathon-prd.md、tmp_idea.md 或任何 .env／憑證檔案。

執行方式
1. 先列出候選賽事與可得的官方公告、作品證據、參賽經驗來源，再選證據最完整的兩場。
2. 瀏覽時優先使用官方來源與第一手作品資料；每個事實旁保留可點擊的直接連結。
3. 寫入前檢查：事實、研究推論與未決問題是否清楚分開；是否把個人經驗誤寫成通則；是否誤將其他賽事套用到台灣站。
4. 完成後執行 git diff --check，並回報：修改檔案、使用的來源、驗證結果、主要限制，以及給非技術讀者的 ELI5 摘要。
5. 不要自行 commit、push、merge 或建立產品決策；完成研究後停下來等待使用者確認。
```

## 使用前提

- 先確認目前工作區是否有他人未提交的變更；只修改本提示詞指定的研究文件。
- 若使用者在新 session 改變研究範圍，以最新指示優先。
