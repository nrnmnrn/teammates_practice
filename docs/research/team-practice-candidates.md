# 團隊實務候選卡

本文件把既有研究轉成未來分配工作時可討論的小型介面。它不是產品規格、台灣站規則或已採納流程；每張卡都要先由團隊決定是否採用。競賽資訊只依原研究標示為參考性先例、證據受限觀察或待確認事項。

## 合格跨案例候選

### `TPC-MVP-001`：以一條可示範的價值鏈與明示邊界組織展示

- **證據／採納狀態：** 跨案例候選；未獲團隊採納。三個參考性案例支持，不能證明是得獎原因。
- **要處理的問題：** 工作若同時服務多個情境，展示敘事與可查驗結果可能失焦。
- **適用條件：** 可辨認一條端到端核心流程，且額外情境會稀釋敘事或降低穩定性。
- **責任模式：** 將「核心流程」與「不處理的邊界」視為同一項可追溯決策；負責該決策者與展示交付者需核對彼此內容，但不預設職稱或人數。
- **預期交付或決策：** 一份輸入至結果的核心流程說明，附明示的範圍邊界。
- **完成證據（若來源支持）：** 可讓他人從輸入看到結果的 Demo；本卡不要求特定提交格式。
- **限制／未推論：** Jayu 與 KeyHaven 沒有公開功能刪減史；不可推論「功能愈少愈好」、固定分工方式，或台灣站偏好。
- **來源連結：** [主題研究](topics/2026-09-winner-mvp-demo-scope.md)；[Jayu](2024-google-gemini-api-developer-competition-online.md)、[Hugo](2025-elevenlabs-a16z-worldwide-hackathon-online.md)、[KeyHaven](2025-bolt-worlds-largest-hackathon-keyhaven.md)。
- **團隊待決定：** 哪一條流程最值得成為共同交付，以及哪些情境明確排除？

### `TPC-MVP-002`：核心流程不穩時，將收斂作為可檢驗取捨

- **證據／採納狀態：** 跨案例候選；未獲團隊採納。Hugo 與 Jayu 支持此研究推論。
- **要處理的問題：** 擴充情境、context 或互動範圍可能使核心流程不穩，阻礙可驗證交付。
- **適用條件：** 已觀察到核心流程受複雜度影響，且可縮小 context、功能或可見互動。
- **責任模式：** 範圍取捨、核心流程驗證與展示敘事互相回報；由團隊決定是否同一人承擔，無固定角色要求。
- **預期交付或決策：** 一項保留／移除／延後的明確範圍決策，及縮減後仍須呈現的核心價值。
- **完成證據（若來源支持）：** 可重播的核心 Demo，用以檢查縮減後的核心價值仍清楚。
- **限制／未推論：** 沒有刪留清單、量化測試或評審回饋；不可推論最佳縮減幅度、固定停止規則或得獎因果。
- **來源連結：** [主題研究](topics/2026-09-winner-mvp-demo-scope.md)；[Hugo](2025-elevenlabs-a16z-worldwide-hackathon-online.md)、[Jayu](2024-google-gemini-api-developer-competition-online.md)。
- **團隊待決定：** 哪些複雜度訊號觸發重新收斂？縮減後如何判定核心價值仍可理解？

### `TPC-FLOW-001`：以可展示核心價值鏈安排工作，保留展示整合交付

- **證據／採納狀態：** 跨案例候選；未獲團隊採納。三場參考性賽事支持；不代表固定職稱、人數、時程或勝因。
- **要處理的問題：** 分工若只看局部工作，Demo 或 Pitch 可能與核心成果脫節。
- **適用條件：** 團隊要把問題、核心處理與展示串成一條可說明的鏈。
- **責任模式：** 各工作交付均連回核心價值鏈；展示整合是明確交付，與其他工作同步校準，非最後才附加的描述工作。
- **預期交付或決策：** 一條工作與展示共用的核心價值鏈，以及展示整合的負責邊界。
- **完成證據（若來源支持）：** 實跑情境或已部署 Demo 支撐展示；末段整合與 review 的記錄可作為內部完成證據。
- **限制／未推論：** Finny AI 的返工資料不足；Project Gandalf 的 slides 內容不可檢查。加入展示整合不能避免 API 或資料依賴失敗。
- **來源連結：** [主題研究](topics/2026-09-team-flow-demo-pitch.md)；[Finny AI](2026-nextgenhack-finny-ai.md)、[Clean Runnings](2022-hack-to-the-future-clean-runnings.md)、[Project Gandalf](2020-nasa-space-apps-project-gandalf.md)。
- **團隊待決定：** 哪些交付必須直接服務核心價值鏈？展示整合由何種交付邊界承接？

### `TPC-FLOW-002`：先辨識會中斷核心展示的外部依賴，保留誠實範圍邊界

- **證據／採納狀態：** 跨案例候選；未獲團隊採納。僅兩個直接支持案例。
- **要處理的問題：** 地圖 API、資料品質等外部依賴失敗，可能改變工作並使 Pitch 出現無法證實的主張。
- **適用條件：** 核心流程依賴外部服務、資料或其他無法完全控制的輸入。
- **責任模式：** 依賴驗證、降級邊界與展示主張彼此可追溯；不指定誰或何時承擔，只要求團隊明確決定責任交界。
- **預期交付或決策：** 高風險依賴清單，及每項依賴失敗時可誠實說明的範圍邊界。
- **完成證據（若來源支持）：** 核心展示不把未證實能力寫成已可用；來源未支持預先 fallback 已存在。
- **限制／未推論：** 不可將加班、臨場修復、犧牲功能或 fallback 視為可複製策略；Finny AI 沒有相應失敗證據。
- **來源連結：** [主題研究](topics/2026-09-team-flow-demo-pitch.md)；[Clean Runnings](2022-hack-to-the-future-clean-runnings.md)、[Project Gandalf](2020-nasa-space-apps-project-gandalf.md)。
- **團隊待決定：** 哪些依賴足以中斷核心展示？各依賴的可接受降級邊界為何？

### `TPC-AI-001`：依交付邊界分配責任；人持有裁決、整合與驗證

- **證據／採納狀態：** 跨案例候選；未獲團隊採納。這是多人 AI coding 批次唯一合格跨案例候選。
- **要處理的問題：** 多人與多種 AI 工具的產出匯入同一 Demo 時，最終責任、方向裁決、整合與可執行驗證可能無人承接。
- **適用條件：** 多人或多工具產出最後須合為同一 Demo。
- **責任模式：** 每個可交付邊界有一名人類可追溯負責；另明示方向裁決、整合與驗證的責任。AI 是執行工具，不承擔最終責任。
- **預期交付或決策：** 交付邊界及其人類負責關係，並決定方向、整合、驗證三項責任如何承接。
- **完成證據（若來源支持）：** 人工檢查、環境／部署處理或 rendering 修正等可執行成果的驗證記錄。
- **限制／未推論：** 三案沒有完整 owner 表；Veritas 不能證明技術階段等同逐人分工。未知最佳負責人數、能否兼任與輪替方式。
- **來源連結：** [主題研究](topics/2026-09-multi-person-ai-coding-alignment.md)；[Recife](2025-recife-vibe-coding-hackathon.md)、[Knowledge Universe](2025-bolt-knowledge-universe.md)、[Veritas](2025-bolt-veritas.md)。
- **團隊待決定：** 哪些責任不可兼任？工作失敗或負責人無法繼續時，如何交接？

## 證據受限觀察與風險

### `TPO-AI-001`：共同意圖與外部邊界先行，再讓 AI 處理有界工作

- **證據／採納狀態：** 降級研究觀察；未獲團隊採納。沒有足夠完整的直接案例支持跨案例候選。
- **要處理的問題：** 互相依賴的工作，可能因不同人或 AI 工作階段對同一概念的理解不同而失配。
- **適用條件：** 至少兩項工作互相依賴，且可能各自解讀同一概念。
- **責任模式：** 共同意圖、詞義、相依輸入／輸出及完成例須有可查版本；團隊另行決定誰裁決詞義與何時允許介面變更。
- **預期交付或決策：** 一份共享的意圖與外部邊界說明；AI 工作只取得當前任務需要的 context。
- **完成證據（若來源支持）：** 來源只支持 shared prompt、shared document、角色及人為修整的部分現象；未支持完整 handoff 或共同文件的完成標準。
- **限制／未推論：** 沒有「語意偏移」衡量或對照組；Recife 無逐隊 prompt／commit，Veritas 無 handoff 文件，Lisbon 尚待查證。
- **來源連結：** [主題研究](topics/2026-09-multi-person-ai-coding-alignment.md)；[Recife](2025-recife-vibe-coding-hackathon.md)、[Veritas](2025-bolt-veritas.md)。
- **團隊待決定：** 是否採用唯一有效版本？誰裁決共同詞義？介面何時能改？

### `TPO-AI-002`：整合、人工返工與可執行檢查是工作風險

- **證據／採納狀態：** 降級跨案例風險觀察；未獲團隊採納。三案只支持風險存在，不支持排程範本。
- **要處理的問題：** AI 產出、環境、部署、prompt 或資料庫問題，可能導致人工返工並壓縮可執行驗證。
- **適用條件：** 作品含多元件、外部 API、database、部署或多種 AI coding tool。
- **責任模式：** 將整合、返工與可執行檢查列為需有人承接的工作類別；分配方式、順序與資源仍由團隊決定。
- **預期交付或決策：** 對整合與驗證風險的明示判斷，以及發生失敗時是否停止加功能或切換備案的決策。
- **完成證據（若來源支持）：** 只支持曾發生手改 code、環境／部署修復、limited application 等結果；不支持固定凍結點。
- **限制／未推論：** 沒有共同時長、逐時記錄或固定凍結點；不支持任何時間比例、code freeze 最佳時點或成功排程。
- **來源連結：** [主題研究](topics/2026-09-multi-person-ai-coding-alignment.md)；[Recife](2025-recife-vibe-coding-hackathon.md)、[Veritas](2025-bolt-veritas.md)、[Knowledge Universe](2025-bolt-knowledge-universe.md)。
- **團隊待決定：** 哪些失敗訊號觸發停止加功能或切換備案？驗證工作由何種交付邊界承接？

## 評審面向的審視鏡頭

以下三張卡只整理公開訊號下可討論的展示證據。評審名單、準則定義、權重、評選程序與提交格式仍待主辦方提供可公開查驗來源；因此它們不是台灣站規則、評分預測或採納決策。

### `TPJ-001`：問題至結果的可查鏈

- **證據／採納狀態：** 證據受限的研究候選；未獲團隊採納。三位評審公開材料支持訊號，非本場偏好證明。
- **要處理的問題：** 展示若無對象、情境、輸入、結果與成功條件的連結，旁觀者難以檢查主張。
- **適用條件：** 準備公開 Demo、Pitch 或作品說明時。
- **責任模式：** 問題定義、可見結果與成功條件成為同一可查交付；團隊決定誰彙整與 review，不預設人員。
- **預期交付或決策：** 一條由使用者／情境、輸入、結果與成功條件構成的展示鏈。
- **完成證據（若來源支持）：** 可觀察的結果連回明確問題；不要求特定報告格式。
- **限制／未推論：** 不推論本場投票、權重、評分偏好或交付格式。
- **來源連結：** [主題研究](topics/2026-09-taiwan-judge-public-signals.md)；[David Chen](2026-sea-openai-taiwan-judge-david-chen.md)、[Oliver Jay](2026-sea-openai-taiwan-judge-oliver-jay.md)、[Thibault Sottiaux](2026-sea-openai-taiwan-judge-thibault-sottiaux.md)。
- **團隊待決定：** 哪個可觀察結果足以支持核心主張？如何表達成功條件？

### `TPJ-002`：把品質與思考做成可見證據

- **證據／採納狀態：** 證據受限的研究候選；未獲團隊採納。David 與 Thibault 的公開材料支持訊號，非本場評分偏好證明。
- **要處理的問題：** 僅宣稱功能很多或「已完成」無法呈現主要失敗情境、取捨與驗證。
- **適用條件：** 作品有可說明的主要失敗情境、限制、替代方案或驗證方法時。
- **責任模式：** 品質證據與取捨理由隨交付一併保存；由團隊決定誰選擇公開內容及誰 review。
- **預期交付或決策：** 一項主要失敗情境與其可重播驗證，及限制、替代方案或取捨理由。
- **完成證據（若來源支持）：** 可重播驗證與人可檢查的限制／取捨說明。
- **限制／未推論：** 不推論評審要求特定測試、文件、深度或格式；公開訊號不等於台灣站規則。
- **來源連結：** [主題研究](topics/2026-09-taiwan-judge-public-signals.md)；[David Chen](2026-sea-openai-taiwan-judge-david-chen.md)、[Thibault Sottiaux](2026-sea-openai-taiwan-judge-thibault-sottiaux.md)。
- **團隊待決定：** 哪個失敗情境最值得呈現？哪些限制與取捨可安全、誠實地公開？

### `TPJ-003`：使 Codex 使用可回查

- **證據／採納狀態：** 證據受限的研究候選；未獲團隊採納。David 與 Thibault 的公開材料支持訊號，非本場要求。
- **要處理的問題：** 工具名稱本身不能說明 Codex 對成果的實質貢獻，也可能誤曝 prompt、內部對話或憑證。
- **適用條件：** 團隊主張 Codex 對建置、debug、測試或驗證有實質貢獻時。
- **責任模式：** 任務與必要 context、Codex 產出、人為 review、可見結果可連成一條鏈；公開範圍由團隊決定並保護私密資料。
- **預期交付或決策：** 一段可公開的使用鏈，說明任務、產出、人為 review 與結果的關係。
- **完成證據（若來源支持）：** 可回查的任務、產出、review 與結果關係；不要求公開 prompt、內部對話、憑證或所有開發紀錄。
- **限制／未推論：** 不推論台灣站要求特定 Codex 介面、帳號、agent 自主開 PR、使用時數或證明格式。
- **來源連結：** [主題研究](topics/2026-09-taiwan-judge-public-signals.md)；[David Chen](2026-sea-openai-taiwan-judge-david-chen.md)、[Thibault Sottiaux](2026-sea-openai-taiwan-judge-thibault-sottiaux.md)。
- **團隊待決定：** 哪些使用紀錄及 review 可安全公開？如何證明沒有盲信工具產出？
