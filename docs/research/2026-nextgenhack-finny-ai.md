## 參考性先例

### 關鍵決策、限制、取捨與結果

**來源直接陳述：** 團隊把 brainstorm 限為 60 分鐘，目標是明確問題、對齊方向並淘汰不成立的想法。概念確定後，分成 development 與 product & pitch 兩軌：前者做 mobile-first MVP、Gemini 與 Cloud Run；後者檢驗 user journey、positioning、簡報，並反覆查看既有 banking app。兩軌當日多次會合對齊；早期與 mentors 的交流幫助他們理解既有功能、技術可行性與真實 gap。[團隊第一手復盤，2026-09-09 查閱](https://www.business-school.ed.ac.uk/about/news/nextgenhack)

**研究推論：** 證據支持「短時限概念決定、兩個並行工作軌、反覆整合檢查、以一個可掃描 live demo 支撐 Pitch」是此隊採用的組合；不支持它必然造成獲勝，也不足以得出適用隊伍人數、精確會合頻率或任何工具選型。

### 候選實務一：早設概念決策時限，淘汰未能支持單一使用者問題的想法

- **來源證據：** 團隊稱 brainstorm 只給 60 分鐘，且以具體「Paris trip」問題收斂；他們表示未嘗試解決所有問題，也不讓 scope creep 進入。[團隊第一手復盤，2026-09-09 查閱](https://www.business-school.ed.ac.uk/about/news/nextgenhack)
- **研究推論：** 面對未知題目時，未來團隊可討論在早期設定一個明確停止點，以「能否解釋單一使用者情境與核心流程」作淘汰依據，保留更多時間完成可展示成果。
- **何時值得討論：** 已知實際賽程、可用人力與選題範圍後，且團隊確實面臨多個同等合理概念時。
- **未來規劃問題：** 誰有權在時間到時作範圍決定？核心使用者情境、不可少的成果證據及可延後項目各是什麼？
- **限制／風險：** 本案五人背景互補，且曾獲 mentor 早期回饋；一小時不必然適合不同題目、資料取得條件或隊伍。
- **待核實項目：** 不知道他們產生多少方案、怎樣比較、是否曾在開發後改題，或每個功能何時決定保留。

### 候選實務二：以 build 與 product/pitch 並行，並預留多次同步而非只在結尾合併

- **來源證據：** 團隊直接稱分成 development、product & pitch 兩軌；後者負責 user journey、positioning、presentation，前者做 MVP 與部署；兩軌多次重新會合以維持 coherence。[團隊第一手復盤，2026-09-09 查閱](https://www.business-school.ed.ac.uk/about/news/nextgenhack)
- **研究推論：** 有不同專長的團隊可討論讓實作與展示敘事同時成熟，並安排短同步點檢查兩者是否仍對同一使用者問題；這不是固定角色模板。
- **何時值得討論：** 團隊有至少一位可持續處理可運行原型、至少一位可處理使用者／商業敘事，且可安全地平行工作時。
- **未來規劃問題：** 每次同步要判斷哪三件事：核心流程能否展示、敘事是否與實際行為一致、哪項不確定性應刪除或明示？誰維護唯一 demo 版本？
- **限制／風險：** 團隊本身說所有人也跨區域貢獻；不能把文章簡化成僵硬分工。平行軌若缺共享驗收標準，反可能造成 demo 與 pitch 脫節。
- **待核實項目：** 未公開實際 meeting 次數、同步格式、版本控制方法、衝突處理或是否有任何返工。

### 候選實務三：以既有產品脈絡與可運行 demo，讓 Pitch 集中證明一件事

- **來源證據：** 團隊稱他們反覆查看自身 banking app，以確認 Finny 接入既有產品；Pitch 把它稱為既有 Cora assistant 的「younger brother」。他們另稱 QR-code live demo 在評審前「做了很多說話」。[團隊第一手復盤，2026-09-09 查閱](https://www.business-school.ed.ac.uk/about/news/nextgenhack)
- **研究推論：** 當題目要求延伸既有系統時，未來團隊可討論把 demo 設計成一個可操作情境，並在 pitch 說清楚現有功能、所補缺口與可觀察結果，而非重述功能清單。
- **何時值得討論：** 主辦提供可查的既有產品或合作方脈絡，而且實際規則允許用公開連結／QR code 展示時。
- **未來規劃問題：** demo 是否能在不依賴未證實資料、帳號或網路下重播？若 live demo 故障，何種錄影或靜態證據可誠實替代？
- **限制／風險：** 本研究未操作 Finny demo；QR code、live demo、NatWest/Cora 的產品脈絡均屬該賽事與該隊處境。將原型說成真實銀行整合會製造誤導與合規風險。
- **待核實項目：** 不知道 demo 腳本、pitch 時長、投影片內容、fallback、網路狀態、評審互動或 QR code 實際掃描成功率。
