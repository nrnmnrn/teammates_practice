## 參考性先例（待核實；不納入已驗證案例／跨案例統計）

### 關鍵決策、限制、取捨與結果

**來源直接陳述：** 活動以 shared vision、預先定義 scope、七隊平行建置不同 capability；AI agents 加速個人執行，但 human discussion、interface negotiation 與最後整合仍是必要工作。作者記錄最後一天仍有 component mismatch 與 manual intervention。[作者第一手觀察](https://schristoph.online/blog/ai-hackathon-observations/)

**研究推論：** 此案支持「AI coding 加速各自內部產出，卻把瓶頸推向共同語意、介面與整合」的單案觀察；不支持七隊、三日、audio、Bedrock 或特定 prompt 方法必然產生較佳結果。

### 候選實務一：人定義 boundaries，AI agent 造 interiors

- **來源證據：** 作者將其總結為「humans own the boundaries, agents own the interiors」；他直接列 API contracts、data models、interface definitions、error handling conventions 為人類需討論、寫下並測試的 spec layer，並稱 component 內部可交給 agent。[作者第一手觀察](https://schristoph.online/blog/ai-hackathon-observations/)
- **研究推論：** 多人 AI coding 團隊可討論把「其他人依賴的輸入／輸出」先變成可查的 shared contract，再讓各 agent 在邊界內自由探索；這是候選做法，不是本隊決定。
- **何時值得討論：** 至少兩個工作單元需交換資料或 API，且介面錯誤會直接破壞共同 demo 時。
- **未來規劃問題：** 誰裁決詞義與欄位？何時凍結 contract？由誰驗證實際 output 與 contract 相符？
- **限制／風險：** 這是作者對七隊的觀察與架構總結，不是逐隊 commit、schema 或 contract test 的獨立證據；spec 過少會限制探索，spec 過多又耗費短時程。
- **待核實項目：** 未知七隊實際是否共同寫 spec、誰批准變更、是否有 contract tests、何種 mismatch 造成返工。

### 候選實務二：共享產品意圖，分拆 capability，保留最後整合緩衝

- **來源證據：** 作者稱七隊各做 individual capability、scope upfront defined、最後合成 combined product；並明確記錄 significant last-day integration work 與 manual intervention。[作者第一手觀察](https://schristoph.online/blog/ai-hackathon-observations/)
- **研究推論：** 若多隊共同交付，產品意圖與 capability 邊界需先共享；時間安排不可把整合當成自動發生，應保留可觀察的整合窗口與 fallback 討論。
- **何時值得討論：** 題目本身要求多個元件共同展示，且單隊不能獨立完成整體流程時。
- **未來規劃問題：** 最小 shared demo 是什麼？每項 capability 的驗收輸入／輸出是什麼？誰持有整合責任？最晚何時停加功能？
- **限制／風險：** 七隊、三日、既有雲帳號與現場協作條件，未必適用小隊或線上活動；沒有官方 timeline、版本歷史或對照組，不能主張此節奏造成成功。
- **待核實項目：** 未找到逐時 checkpoint、code freeze、rehearsal、fallback demo 或各隊負責人名單。

### 候選實務三：把 AI activity visibility 當探索訊號，不當品質分數

- **來源證據：** 作者公開 leaderboard repo，並稱 dashboard 以各 AWS account 的 Bedrock token metrics 顯示 iteration activity；他也承認 token consumption 是 activity，不是 quality judgment，retry loop 可能浪費 token。[技術紀錄](https://schristoph.online/blog/hackathon-in-a-hackathon/)；[repository](https://github.com/stechr/bedrock-hackathon-leaderboard)
- **研究推論：** 在學習或探索階段，低風險的 activity signal 可能幫助團隊發現停滯；若用於評分、排名或資源分配，則需另加 quality、integration、test 與 demo evidence。
- **何時值得討論：** 團隊有明確同意的 AI usage visibility、各人帳號隔離與安全權限，且 leaderboard 只作回饋，不作得獎或人員評價。
- **未來規劃問題：** 是否取得同意？哪些 metrics 不應公開？如何防止 token 競賽鼓勵無效 retry、成本失控或暴露個人活動？
- **限制／風險：** 這是作者自建工具與單一事件的觀察；AWS Bedrock、CloudWatch、跨 account IAM、token pricing 與 Kiro 均屬該環境，不能默認可用。
- **待核實項目：** 未知團隊是否同意公開 metrics、是否發生過量消耗、leaderboard 是否影響 quality 或僅影響 activity。
