# 黑客松主題批次研究指南

使用本指南研究一種可比較的黑客松經驗，例如 AI-assisted 開發的返工、Demo 取捨或多人協作。批次是多個獨立案例的協調與比較；Deep Research 只可作為一次性的候選地圖，不是多案例正式紀錄。目標是提出可追溯的參考性先例與跨案例候選，不是替本隊選題、制定流程或確認台灣站規則。

共通的來源分級、案例最低資訊要求、候選實務六欄、狀態與升級邊界，均以[研究記錄規格](research-record.md)為唯一準則。本指南只處理主題批次的選擇、執行、部分失敗與收斂。

## 研究契約

題目明確時，主 agent 先建立只含研究契約的主題摘要後直接執行；題目過廣時，先提出可比較的子題並等待使用者選擇。所有案例覆核後，再補完同一份摘要並更新索引。每份契約至少包含：

- 批次 ID、日期、核心研究問題與適用範圍。
- 納入／排除條件，以及四至六個共同比較問題。
- 目標為三個**已驗證案例**、最多篩選八個**候選案例**，並優先涵蓋至少兩場競賽。
- 所需來源組合、輸出檔案路徑、停止條件與台灣站不可套用界線。
- 題目中容易歧義的用詞及其可由來源支持的納入定義；例如研究 `vibe coding` 時，定義為參賽者可追溯地描述 AI 產碼或修改與後續返工的經驗，而非研究者自行推測。

「候選案例」是尚未完成查證的一個團隊／作品；「已驗證案例」符合 `research-record.md` 的證據標準；「競賽」是案例所屬事件；文章、影片與 Demo 都是來源，不能拿來源數量計算案例數。 「跨案例候選」則是整合後的做法，不能與候選案例混稱。

## 建立與篩選候選池

1. 先檢查既有案例是否符合本批題目。重用前重新確認官方成果／參賽證據、可檢查作品、必要的第一手紀錄、資訊分類及事件／作品識別；不符合者只可作背景或待核實資料。
2. 收集最多八個候選案例的精簡線索：事件、團隊／作品、官方或提交證據、作品證據、第一手紀錄、來源連結及暫定納入／排除理由。不要保存來源全文，也不要為被排除候選建立正式案例檔。
3. 依下列順序選案：與題目相關性、第一手決策與困難資訊、官方證據、可檢查作品、多樣性，最後才是名次或熱門度。多篇文章談同一團隊／作品時是一個案例的證據組合；同一團隊原則上每批只計一次。
4. 主動搜尋反例，例如返工、失敗 Demo、放棄工具或未完成的第一手經驗。在摘要記錄反例搜尋方向、納入／排除結果，以及未找到反例不代表不存在。

題目寬、來源分散或互相矛盾時，若使用者已授權 Deep Research，主 agent 可在本主題最多一次使用 `$deep-research-work:deep-research` 建立暫時候選地圖。地圖最多八案，每案列出官方、作品與第一手來源線索、可研究面向、納入／排除理由、衝突與證據缺口；完整引用報告只作工作底稿，不存入 repo。題目已窄且已有可直接驗證的候選時，略過此步，直接查證。

優先選擇不同團隊／作品，並至少涵蓋兩場競賽。兩個同場案例可形成僅限該環境的候選；只有跨競賽的可比較證據才可描述為較廣泛的黑客松候選。

## 逐案研究與工作分工

每個入選案例各自以 `$research` 做輕量、來源嚴格的查證；其產出是一份 `docs/research/YYYY-event-project[-team].md` 案例檔。任何 worker 在取得最低證據組合前不得建立看似正式的案例檔；證據不足時回報排除原因，由主 agent 考慮下一候選。僅在使用者已授權 Deep Research，且來源互相矛盾、第一手資料難取得或關鍵流程證據缺失時，主 agent 可升級該案為來源稽核；稽核不另建長篇案例報告，僅供更新原案例檔與標示剩餘缺口。

平行工作時：

- Sol 保持主 agent，負責研究契約、候選排序、來源與分類覆核、主題整合及索引更新。
- Luna 負責候選搜尋、去重與可重複的來源檢查。
- Terra 一人負責一個案例檔，處理需要判斷的查證與撰寫。
- 完成後安排新的唯讀 reviewer，僅檢查證據連結、計數、資訊分類、反例、台灣站誤套與跨案例主張；reviewer 不直接改檔或升級狀態。

每份案例檔只有一位 writer；只有主 agent 可修改主題摘要、研究總覽及跨案例狀態。若指定角色不可用，依 repo 的 agent routing 規則停止並回報，不以其他角色取代。

暫時性網頁或工具問題可重試一次。來源不足、作品無法檢查、重複案例或關鍵來源互相矛盾時，標示個案排除／待核實並改用下一候選；不得把半成品算入已驗證案例。

## 主題摘要與收斂

所有案例完成主 agent 覆核後，補完先前建立的 `docs/research/topics/YYYY-MM-topic-slug.md` 主題摘要，再更新 `docs/research/sea-openai-winning-patterns.md`。主題摘要至少包含：

- 研究契約、執行進度、候選池與排除理由。
- 納入案例的連結、共同比較表、支持與反例。
- 每項跨案例候選的支持案例、反例／不支持案例、研究推論、適用條件、限制與待確認問題。
- 資料偏差、來源集中、連結失效等風險，以及不可套用台灣站的內容。

主題摘要不承載未回鏈的事實；每項結論都要連至對應案例檔與其來源。案例數量不是因果證明或成效保證。

批次的工作進度與證據狀態分開：

| 結果 | 執行進度 | 跨案例候選 |
| --- | --- | --- |
| 三個已驗證案例 | 完成 | 依比較結果判定 |
| 已篩選八案後取得兩個已驗證案例 | 完成但證據受限 | 可以，但明確限縮範圍 |
| 一個或零個已驗證案例 | 研究不完整 | 不可提出 |

單一案例維持「案例觀察」。所有跨案例候選都仍未獲團隊採納，除非有另行記錄的明確決定。

## 完成與邊界

完成前，主 agent 與 reviewer 都要確認：每個正式案例符合證據標準、計數與可比性正確、每項結論可回鏈、反例與未知事項已處理，且沒有把其他賽事寫成台灣站規則。執行 `git diff --check`，並檢查主題摘要和總覽中的內部文件連結。

本批次只建立研究案例、主題摘要與總覽導覽。保持 `team-playbook`、角色分工、時程、工作流程與產品規格不變，也不修改 `build-handoff/` 或 `TODO.md`。不讀取、修改或暫存 `hackathon-prd.md`、`tmp_idea.md`、`.env` 或任何憑證檔案；不 commit、push 或 merge。回報修改檔案、資訊分類、跨案例門檻、尚未採納的候選、資料缺口／風險、下一步、ELI5 摘要，以及 `team-playbook`、`build-handoff/`、`TODO.md` 是否被觸及，然後等待使用者指示。
