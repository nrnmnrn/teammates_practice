# 承接操作手冊

本頁是實作 repo 的精簡操作入口。流程已獲使用者核可，跨隊員演練仍未驗證；實作須等正式開發窗口。驗收案例見 [ACCEPTANCE](ACCEPTANCE.md)，環境命令見 [README](README.md#環境與從零啟動)。具體工作拆分、owner、順序與相依待團隊決定。

## 接到工作

1. 讀 AGENTS、CONTEXT、ARCHITECTURE、母 PRD 與完整驗收案例；再讀團隊決定的當前工作。
2. 短檢查：交付結果與驗收清楚、工作未被他人認領、同檔修改已協調。可認領者登記後開工；有衝突先協調。
3. 團隊核准具體拆分後，通常每份子 PRD 拆為 2 張、最多 3 張 Ticket；以領域命名。未來集中目錄建立後，父 issue 對應子 PRD、子 issue 對應 Ticket。未經團隊決定，不建立實際名稱、編號、owner、順序、相依或連結。

## 依情境選 skill

| 情境 | 做法 | 必須得到的結果／限制 |
| --- | --- | --- |
| 缺資訊、規格矛盾、驗收卡住且原因不明 | `$caveman:investigate-first`，分開症狀與推論，查證輸入、狀態及責任 | 可查證原因或精確 blocker；涉及需求取捨交由人決定 |
| 明確 Ticket 已就緒 | `$implement` 管實作、相關測試及 `/code-review`；適合先寫測試的行為使用 `$tdd` | 本票的驗收與測試結果；覆寫上游自動 commit，留待 closeout 核可 |
| 需要定位、兩檔內有界修改或精簡審查 | `$caveman:cavecrew` 對應 investigator、builder、reviewer；每組檔案一位寫入者 | 有位置的證據、窄範圍變更或 findings；跨多檔交一般實作者，不強塞給 builder；不保證總 token 或正確率改善 |
| 程式錯誤難重現、偶發或原因不明 | `$diagnosing-bugs`，先建立能抓住原症狀的檢查，再驗證假設 | 重現命令、原因及回歸驗證；簡單且已定位問題可說明理由縮短流程 |
| 實作及必要驗證完成 | `$task-closeout`，對照需求、證據、Git 所有權與下一步 | 狀態核對及精確 commit 批准請求；未完成或 blocked 不宣稱 closeout 完成 |
| 換 session，或要移交仍 blocked 的工作 | 詢問使用者是否 `$handoff`，獲同意後寫 OS 暫存目錄 | 記未被現成文件涵蓋的進度、假設、阻礙、下一步與建議 skills；既有規格、issues、diff 只引用，不重複抄寫 |

上表是路由，不是替代 skill 全文；先確認該成員環境實際有對應 skill。缺少時回報缺項與受影響步驟，不假裝已執行。需要安裝時依使用者授權處理。

執行範例：

> 請依目前 Ticket 執行 `$implement`，完成實作、測試與 `/code-review`；不要 commit。完成必要驗證後執行 `$task-closeout`，列出檔案與完整 commit 訊息供我核可。

既有明確 commit 授權持續有效；核對本次檔案及授權範圍後執行，不反覆詢問。Push、merge、發布另依授權，不從 commit 同意推定。`/compact` 完全自行判斷，沒有強制時點，不影響開工、驗收或交接資格。

## 卡住與完成

- 同一 blocker 超過 15 分鐘，或兩次有證據嘗試仍未解，標為 Blocked。留下原症狀、已試方法及結果、缺什麼、由誰提供；必要紀錄先遮蔽敏感資訊。可以 handoff，不能關票冒充完成。
- Ticket 完成：本票驗收與相關測試、AI review 通過，留下證據與授權後的 commit；無需每票另開 PR 或共同驗收。若 commit 待批准，明記待批准，不說已提交。
- 團隊已核准子 PRD 後：全部 Tickets、完整功能與必要測試、最後 AI review、作者自查通過；至少另一隊員共同確認，經授權合併，再於 `main` 驗證整合。父 issue／PR 留下驗證版本、後端來源、預期與實際結果及審查證據；全部子 PRD 通過後仍須完成 [整體驗收](checklist.md)。
- Closeout 完成後可問是否 handoff；未換 session 無須每票強制產生交接文件。
- 使用者不懂時，採 ELI5（白話解釋）：說明改了什麼、為何需要、一個生活例子、未知事項與下一步需要誰做。不能只列術語或一句「已完成」。

想像施工看板：先確認材料及前一段工程可用，再領取小份施工單；驗收證據是完工依據。卡住就寫清缺件，下一人才能續作，不能把未驗證的房間當作已交屋。
