# 實作 repo 操作規則

本檔與本交接包一起帶入開賽後的實作 repo。在規劃 repo 內只維護文件，不建立競賽程式；開賽與交接限制見 [README](README.md)。

## 承接入口

- 開始工作時，讀 [CONTEXT](CONTEXT.md) 的領域詞彙、[ARCHITECTURE](ARCHITECTURE.md) 的實作位置與責任、[PRD](PRD.md) 共用規則、[ACCEPTANCE](ACCEPTANCE.md) 完整案例與團隊決定的當前工作。
- 開始、卡住、完成或換 session 時，依 [WORKFLOW](WORKFLOW.md) 判斷步驟與 skill。
- 文件定義需求與驗收案例；具體子 PRD、owner、工作順序與相依待團隊決定。核准後通常每份子 PRD 有 2 張、最多 3 張以領域命名的 Ticket；未來集中目錄建立後，GitHub 父 issue 對應子 PRD、子 issue 對應 Ticket。
- 開工先核對當前工作與驗收範圍；同檔修改先協調。一次 session 做一張可執行 Ticket。

## 實作與權限

- 先說明假設、成功條件及範圍，再做最小修改；沿用現有模式。資訊缺漏或規格衝突先查證，需要取捨時交由人決定。
- `$implement` 在本 repo 負責實作、測試與 `/code-review`；覆寫其自動 commit 預設。完成必要驗證後由 `$task-closeout` 核對並提出 commit 批准；已有明確授權時依授權範圍執行，不反覆詢問。
- 未批准不得 push、merge 或 deploy。于喬保留既有最終合併角色；共同驗收不等於合併授權。
- 新依賴、資料庫結構、認證／授權、CI/CD 或刪除／跳過測試，先取得使用者同意。
- 修改公共行為時更新相關測試；明確處理錯誤，診斷使用專案 logger。不可弱化驗證使測試通過。
- 保留既有未提交修改；只提交本次所屬變更。不得略過 pre-commit hooks；commit 僅列人類作者。

## 子代理分工

- 每位 worker 都要有明確範圍、限制、產出及完成證據；隔離上下文，同一組檔案一位寫入者。獨立審查交給未參與寫入的唯讀代理。
- 指定模型不可用時回報，不自行換模型。產品、權限與發布批准仍由使用者決定。

## 環境與檢查

- 使用 `uv`；實際版本、安裝、啟動與驗收命令以 [README](README.md#環境與從零啟動) 和實作 repo 配置為準。每位隊員使用自己的虛擬環境。
- 程式變更執行相關測試、lint 與格式檢查；有型別檢查配置才執行其指定命令。完成整份子 PRD 時執行完整檢查。
